# Hand-written SQL over D1, without an ORM

Data access goes through a thin helper in `app/db.server.ts` (`dbQuery`) that wraps D1's prepared statements, with the SQL written by hand in `app/models/*.server.ts`. It began as three — `dbQueryRow` and `dbExecute` were later removed, having never been called; the site does not write on the request path. No ORM, no query builder, and no migration tool: `seed/d1/schema.sql` is applied by hand and `seed/d1/seed.sql` is regenerated in full rather than migrated.

The site has one table that matters and four read queries against it, none of which joins. An ORM's value — relationship mapping, migrations, query composition — has nothing to work on here, while its cost is real: bundle size in a Worker, a schema definition that duplicates `schema.sql`, and an abstraction between the reader and the two partial unique indexes that encode Post and Bookmark identity.

## Consequences

- Column-to-field mapping is done in SQL (`id_content as "idContent"`), so it lives next to the query rather than in a separate mapping layer.
- Row types (`ContentRowType`) are hand-maintained and **not** checked against the schema by the compiler. A column rename still breaks at runtime rather than at `tsc` — but no longer only in production: the integration tests run the real queries against a seeded D1, so a renamed or dropped column fails `pnpm test`. That is a smoke alarm, not a type system; it catches the columns the tests actually read. Row types are shaped after the domain rather than the table: a discriminated union on `type`, so the columns a Post or a Bookmark does not carry are typed `null`.
- Schema changes are a manual two-step: edit `seed/d1/schema.sql`, then apply it to local and remote yourself. There is no migration history and no rollback. Forgetting the remote half is no longer silent — `seed/verify-schema.ts` compares the deployed schema against this file as the first step of every publication and refuses to seed when they differ — but it blocks, it does not migrate. The applying is still yours. **Superseded by ADR 0006**, which moves the deployed database onto `wrangler d1 migrations` and keeps `schema.sql` as the declared shape. The decision against an ORM and a query builder is unaffected: the arguments above are about what ships inside the Worker, and a CLI does not.
- This is a deliberate deviation from the default modern choice. Reopen it if the schema grows relationships worth mapping — not merely because Drizzle or Prisma is available.
