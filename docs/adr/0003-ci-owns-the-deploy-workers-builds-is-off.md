# CI owns the deploy; Workers Builds is off

A push to `main` used to start two independent things that never learned about each other: the CI `seed` job, which wrote the deployed D1 and KV, and Cloudflare's Workers Builds, which built and deployed the Worker on its own side. Nothing ordered them and nothing failed when only one succeeded. Workers Builds is now disconnected and `.github/workflows/ci.yml` runs the whole publication in one job — verify the deployed schema, seed both stores, read them back, build, `wrangler deploy`, then confirm the uploaded version is the one serving.

## Considered Options

- **Seed after the deploy.** Keep Workers Builds and have CI wait for its check to conclude on the same commit. Rejected: it means polling another system's status to derive an ordering neither system enforces, and it does nothing when the seed is the half that fails — by then the code is already live.
- **Verify rather than order.** Let both run and assert afterwards that the deployed Worker and the stores agree with the repository. Rejected: it detects instead of prevents. The site has already served the mismatch by the time the assertion runs, and it needs the Worker to expose its build SHA, which is a new public surface built solely to observe a problem we can remove.
- **Keep Workers Builds for `dev` previews only.** Rejected because it is not offered: branch control has no switch that stops the production branch from deploying. The only lever is neutering the production deploy command, which leaves every push building twice. The previews turned out to be worth nothing anyway — `preview_urls` defaults to `workers_dev`, which is `false` here, so the version uploads had no usable URL behind them.

## Consequences

- **The API token gained `Workers Scripts:Edit`.** It was deliberately scoped to `D1:Edit` and `Workers KV Storage:Edit`, and widening it is a real cost. It is a smaller one than it looks: the Worker does not sanitise at read time, so `Workers KV Storage:Edit` already bought an attacker stored HTML — script execution in a visitor's browser, on this domain. The new permission adds the server side to a compromise that was already serious. One token rather than two, because both would live in the same GitHub Environment and be readable by the same jobs; splitting them separates which step *uses* which, not who *can*.
- **Seeding happens before deploying, and that order is the failure mode we chose.** If the deploy fails, old code serves new content, which is almost always harmless because the common change is adding a Post. The reverse — new code over old content — 404s a Post that was just published. Neither order survives a change to the *shape* of a KV payload during the seconds the deploy takes; only splitting such a change across two merges does, and that is discipline, not a guarantee this workflow provides.
- **Runs on `main` queue instead of cancelling.** `cancel-in-progress` is now an expression, false only on `main`. A cancellation landing between the seed and the deploy would recreate the exact split this removes. Note the limit: it protects against concurrency-driven cancellation only, not a manual cancel or an expired `timeout-minutes`, which is why the job's timeout is generous.
- **Build and deploy must stay in one job.** `wrangler deploy` finds the built Worker through `.wrangler/deploy/config.json`, a gitignored build artefact written by `@cloudflare/vite-plugin`. On a runner without it, wrangler falls back to the root `wrangler.jsonc`, whose `main` is the unbuilt entry point and which declares no assets — a green run shipping the wrong Worker.
- **`wrangler.jsonc` must keep no `route`/`routes` key and `workers_dev: false`.** That is Cloudflare's documented configuration for "the dashboard owns the routes", and it is what keeps `poschuler.com` attached. Adding a `routes` key would hand that over to Wrangler. Secrets are safe either way: `wrangler deploy` never deletes them.
- **Build logs before the switchover live only in Cloudflare's history**, and Cloudflare does not document what disconnecting keeps.
- **The run cannot check that the site serves.** The first attempt did exactly that and failed on its first execution against a perfectly healthy site: Bot Fight Mode challenges automated clients from datacentre networks, and it cannot be skipped by any rule on this plan. The last step therefore confirms the uploaded version is live rather than that it works — a real gap, recorded under Known defects, and one that belongs to continuous monitoring rather than to this workflow.
