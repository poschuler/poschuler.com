# The model is the DSL, and the diagrams are generated from it, never drawn

`architecture/workspace.dsl` is 293 hand-written lines of Structurizr DSL, and it is the only file in this repository anyone edits by hand to change the architecture picture. One model stands behind eight views — a context, two container views split by tense, two component views, two dynamic views and one deployment view — so an element declared once appears in every view that includes it, under the same name, with the same tag. The thirty-two SVGs under `architecture/diagrams/` are exported from that model by `pnpm run diagrams`; none of them is drawn, and a change to any of them that did not come out of the DSL is a defect. `architecture/workspace.json` belongs to Structurizr rather than to us and is committed for one reason, recorded below. The prose keeps its authority: `architecture.md` is where the *why* lives, every description in the DSL is one line naming a single responsibility, and where the reason matters the DSL names an ADR number instead of paraphrasing the paragraph that owns it.

The decision this really makes is that the architecture picture is **source**, subject to the same treatment as everything else generated here. It is parsed in CI and a broken workspace fails the run, exactly as a fixture that no longer matches its Markdown does.

## Considered Options

- **Diagrams drawn by hand and committed as images.** Rejected, and it is the option this ADR exists to make hard. A drawing has no relationship to the code it depicts, so it goes stale silently and there is no step that can notice — the same defect `check:fixtures` exists to catch one directory over, with the additional property that no verifier is even possible. It also cannot answer a structural question. "Which views does the KV uploader appear in" is a search of the DSL; over a folder of images it is a person opening files.

- **Prose only, and no model.** `architecture.md` is 399 lines and says more than any diagram can, which was the strongest argument against adding a second thing to keep in step. Rejected as *sufficient*, never as authority — it stays the authority. Two things it cannot do are the two this system most needs said. It cannot put the runtime tense and the build tense side by side, which is where almost everything characteristic of this repository lives: the Markdown tree that is the source of truth, the committed fixtures, the four verifiers, none of which run inside the Worker. And it cannot say *in that order* in a way a reader can see at once — migrate, verify the schema, seed, verify the stores, deploy, verify the deployment, in one job, for the reasons ADR 0003 and ADR 0006 give. That order is the architecture, and the dynamic view of the Publication is the only place it is visible rather than recounted.

- **Mermaid, or any diagram-as-code embedded in the Markdown.** The obvious one, and the one that looks best in hindsight: GitHub renders it natively, there is no Docker, no export step and no generated artefact to commit. Rejected because it has no *model*. Every diagram is its own drawing that happens to be written in text; an element appearing in three diagrams is three unrelated strings, nothing relates a container to the components inside it, and there is no level structure to move between. Eight views over one model is the thing being bought, and Mermaid does not sell it. The cost of that purchase is real and is listed below.

- **A hosted workspace, on the Structurizr cloud service.** Rejected, and this repository has already paid a small instalment of the reason. The workspace was written with `theme default`, which is fetched from `https://static.structurizr.com/themes/default/theme.json`; that service reaches end of life on 30 September 2026, and the exporter warned about it on every run. Removing the theme cost one line of `styles` once it was measured — every exported view came out identical to the pixel without it. A model that lived there rather than in this repository would not have been one line.

## Consequences

- **`workspace.json` is committed, and its diff is unreadable by construction.** 2 181 lines, of which **eight elements carry a position anyone chose**. The rest is the model re-serialised out of the DSL, plus the entire DSL a second time as a 32 KB base64 string on one line, plus twenty lines of `containerInstance` identifiers that Structurizr mints fresh on every parse and that therefore change when nothing has. That redundancy is the price of the eight, and the eight are the hand-placed steps of the Publication: seven of the eight views need only the right `autolayout`, and the one whose entire reason for existing is the order is the one no algorithm can lay out — left to itself it ordered the steps 7, 2, 4, 5, 3, 6, 8. Read the DSL diff; the JSON diff is not for reading.

- **A clone needs one local git setting that cannot travel with it.** `.gitattributes` declares `architecture/workspace.json filter=structurizr`, and the filter itself is per-clone configuration: `git config filter.structurizr.clean "jq -S 'del(.lastModifiedDate)'"`. A clone without it is not broken — git stores the file unfiltered — but the first save after opening the workspace shows a one-line diff that means nothing. It also puts `jq` on the list of things this repository assumes.

- **Docker is required to look at the model and to export it, and the exporter is large.** Reading the committed SVGs needs nothing, which is why they are committed. Everything else needs a container: `structurizr/structurizr` at 431 MB serves the workspace and parses it, and the `-playwright` tag at 3.49 GB is what renders, because rendering needs a browser and only rendering does. Both are pinned to one release, including the one `docker-compose.yml` runs — the instance that serves the workspace is also the thing that rewrites `workspace.json`, so an unpinned one would sit upstream of a pinned renderer.

- **The DSL is verified in CI; the SVGs are not.** The asymmetry is deliberate and the two halves decided each other. A broken DSL is otherwise *invisible* — Structurizr Lite rewrites `workspace.json` after every successful parse, and when the DSL later stops parsing it serves that file in silence, answering 200 from the page and from the API with the last good model and logging nothing. So the browser cannot be the thing trusted, and the last step of the `verify` job parses the DSL instead. Checking the SVGs the same way would mean pulling 3.49 GB on every run to verify files only a person reads, so nothing does: they can go stale, and the only thing that notices is somebody reading the diff.

- **Because that is true, the export has to be deterministic, and it did not start out that way.** Every diagram renders the workspace's save timestamp in a footer no flag can suppress, and Lite rewrites that timestamp whenever it serves a page — so all thirty-two files differed after merely opening the workspace, and a diff that fires every time carries no information. Deleting the field makes it worse rather than better: absent, the exporter stamps the moment the export ran. `scripts/export-diagrams.sh` pins it to a constant in a staged copy of the workspace, which is why the footer date on every diagram is not a date.

- **One palette has to survive two backgrounds.** The diagrams are exported light and dark, and `-mode dark` paints the canvas and the arrows but does not touch element colours — while Structurizr styles are per workspace, so one model cannot carry two palettes. Every element colour therefore has to clear 3:1 against white *and* against `#111111`, which is a luminance band from 0.116 to 0.300, and four of the eight had to move into it. The C4 ladder — person, system, container, component, darkest to lightest — still reads, but at 1.34x, 1.26x and 1.38x apart, which is as much separation as a band 2.6x wide holds for four steps.

- **Two of Structurizr's own inspections fail permanently, on purpose.** `missing documentation` and `missing decisions`, because neither `!docs` nor `!adrs` is used. The prose is not embedded because `architecture.md` is the most heavily cross-linked file here and none of its relative links resolve once it is rendered inside a workspace — the document that would gain most from being embedded is the one that would break most. The ADRs are not embedded because `!adrs` takes the first four characters of every filename in the directory as a decision number, so `docs/adr/README.md` fails the entire workspace with `NumberFormatException: For input string: "READ"`, and every way around that costs a move inside `docs/`. This index is worth more where it is. Both errors are deliberate and this line exists so that neither is later read as an oversight and fixed.

- **The model indexes the prose and must never restate it.** One line per description, naming a single responsibility, and an ADR number where the reason matters. A diagram that repeats a paragraph drifts from it within two commits; one that points at it does not. The rule has a second half that is easy to lose: no element may appear that cannot be pointed at a file, which is what keeps the picture a description of this repository rather than of a system like it.
